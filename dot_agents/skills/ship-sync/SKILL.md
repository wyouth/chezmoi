# Ship Sync

两阶段流程：**阶段 A 只准备并停住**；**阶段 B 仅在用户确认后**才 commit 并 push。

原名 `git-sync-push`；调用用 `/ship-sync`。

## 硬约束

- 阶段 A 结束前：不 `commit`、不 `push`、不 `--force`。
- 阶段 B：用户明确确认后，才一次性 `commit` + `push`。
- 不改 git config；不用 `-i`；不用 `--no-verify`（除非用户明确要求）。
- 不提交疑似密钥文件（`.env`、`credentials.json` 等）；若用户点名要提交，先警告。
- **门禁未通过则硬停**：不 stash、不 pull、不生成「可继续同步」的确认包；用户修完后重跑本 skill，或明确说「忽略门禁继续」后才放行。
- **未跟踪文件默认纳入提交**：见下方「拟提交范围」；不得因「主题不相关 / Speculative Generality / 另开 PR」等主观理由擅自从拟提交集合中剔除。

## 拟提交范围（含新增未跟踪文件）

`git status` 中的 **modified / staged / untracked** 一并视为候选提交集，**默认全部纳入**确认包「将纳入本次提交的变更」。

| 可自动排除（写入确认包「排除项」并说明） | 不得自动排除（须默认纳入） |
| --- | --- |
| 疑似密钥（`.env`、`credentials.json`、含明文 secret 的本地配置） | 任意 `docs/**`、设计稿、方案 md（含未跟踪） |
| 明确的构建/运行时产物（`dist/`、`*.map`、日志、临时目录等，且通常已被 ignore） | 源码、测试、migration、前端页面等新增路径 |
| 用户在本轮已点名排除的路径 | 门禁/neat 认为「范围混杂」但仍是合法工作区文件 |

- 门禁可对「主题是否该同批」写**建议**，但确认包默认计划仍是**纳入**；若建议排除，须单独列「建议排除（待你确认）」——**用户未同意前，阶段 B 仍按纳入执行**。
- 仅当用户在确认回复中明确排除某路径后，阶段 B 才可不 `git add` 该路径。
- 阶段 B `git add` 前再跑一次 `git status -u`：确认包写明纳入、却仍未跟踪的路径必须补 add；漏加视为流程失败，须补提交或向用户说明。

## 阶段 A — 准备（停住等确认）

按序执行；每步失败则停止并说明原因与可选回滚。

**顺序不可颠倒**：摸清现状 → 门禁（硬停）→ 再保全/拉取 → 再合并冲突 → 最后确认包。

### 1. 摸清现状

并行执行：

- `git status -u`（未跟踪文件须完整列出，勿只显示目录名就漏文件）
- `git diff` / `git diff --staged`
- `git branch -vv`（看 upstream）
- `git log -5 --oneline`（对齐近期风格，但文案仍用下方全局默认格式）

完成标准：已知当前分支、是否跟踪远端、本地改动范围（**含全部 untracked**）、是否已有冲突/rebase 进行中；并已按「拟提交范围」形成默认纳入清单。

### 2. 门禁（拉取之前；未通过则硬停）

在 stash / pull 之前审查**当前本地拟提交改动**（`git diff` + `git diff --staged`，**含全部默认纳入的未跟踪文件**）。固定点：当前 upstream（`@{u}`）；无 upstream 时用 `HEAD`。审查对象是工作区相对该基线的拟提交内容，不是「已提交的 HEAD 三点 diff」 alone——未提交 hunk 与未跟踪新文件必须纳入审查。

#### 2a. 主门：code-review（始终执行）

- 读取并遵循同目录旁的 `code-review` skill（`~/.agents/skills/code-review/SKILL.md`）。
- 无独立 spec 时：Spec 轴记「无 spec」，以 Standards + 风险为主；不阻塞流程去追问 spec，除非用户事先指定了路径。
- 无本地改动可审时：记「无本地改动」，跳过双轴审查正文，主门视为通过。
- **未通过（硬停）**：结论为「建议先改」「勿提交」，或存在未消除的缺陷级发现 / 疑似密钥 / 明显破坏性改动。输出审查摘要与待改项后**停止**，不进入步骤 3。
- **通过**：建议为可提交（或「无发现」且无阻塞项）→ 进入 2b 判定。

#### 2b. 辅门：neat-freak（仅触及知识面时）

若拟提交路径触及任一知识面，则再跑 neat-freak；否则记「未触发」并跳过。

知识面（路径匹配，大小写不敏感；目录前缀亦算）：

- `**/AGENTS.md`、`**/CLAUDE.md`、`**/.cursor/rules/**`
- `**/CONTEXT.md`、`**/README.md`、`docs/**`
- `**/.agents/**`、skills 目录（`**/skills/**`、`**/SKILL.md`）
- 项目内明确的规则/记忆入口（若现场规则另有声明，一并计入）

执行时：

- 读取并遵循 `~/.agents/skills/neat-freak/SKILL.md`。
- 默认 **文档同步** 档 + **轻量路径**；仅当现场规则要求完整收尾/发布流程时升到完整路径。
- 范围锚定本次拟提交改动及其直接影响的文档/规则面；不擅自扩大到无关清场删除。
- **未通过（硬停）**：存在阻塞级矛盾（文档与代码明显不一致且未处理）、疑似密钥、或 neat 结论要求先改而尚未处理。输出结论与待改项后**停止**，不进入步骤 3。
- **通过**：无阻塞项（`pending` 可保留在确认包里，但不阻止继续）→ 进入步骤 3。
- 用户明确「忽略门禁继续」时可跳过未通过的门；须在确认包中标注已忽略及原因。

完成标准：主门已通过（或用户明确忽略）；辅门已通过、未触发、或用户明确忽略；且尚未 stash、尚未 pull。硬停时本条不成立。

### 3. 保全本地改动

有未提交改动时：

```bash
git stash push -u -m "ship-sync: wip before pull"
```

无改动则跳过 stash，并在确认包里注明。

完成标准：工作区干净，或已明确记录 stash ref（`stash@{0}` 等）。

### 4. 拉取（merge）

```bash
git pull --no-rebase
```

完成标准：pull 成功，或已进入可处理的 merge 冲突状态（不是未知失败）。

### 5. 恢复本地改动

若步骤 3 做了 stash：

```bash
git stash pop
```

`stash pop` 产生冲突时，保留冲突标记，进入步骤 6。pop 失败且 stash 仍在时，不要丢弃该 stash。

完成标准：本地改动已叠回，或冲突文件列表已完整列出。

### 6. 合并冲突

对每个冲突文件：

| 情况 | 动作 |
|------|------|
| 语义明确（格式-only、明显一方过时、机械合并） | 直接解完并 `git add` |
| 业务语义不明、删改意图冲突、两端逻辑都可能对 | **不猜**；列入待确认 |

完成标准：可自动项已全部解决并暂存；不确定项路径 + 双方差异摘要已备好。

### 7. 生成确认包（必须输出后停住）

一次性输出以下结构，然后**停止，等待用户确认**：

```markdown
## 待办 / 结果确认包

### 同步摘要
- 分支：
- 远端：
- stash：已做 / 未做（ref：）
- pull：成功 / 冲突中
- stash pop：成功 / 冲突 / 未执行

### 门禁
- 主门 code-review：通过 / 已忽略（原因）
  - 基线：
  - Standards：…（或「无发现」）
  - Spec：无 spec / …
  - 风险摘要：一句话
  - 建议：可提交 / …
- 辅门 neat-freak：通过 / 未触发 / 已忽略（原因）
  - 触及的知识面：（路径或「无」）
  - 摘要：一句话（未触发则写「—」）
  - 遗留 pending：（若有）

### 已自动合并
- `path`：做了什么（一句话）

### 待你处理的冲突
- `path`：冲突要点 + 请你决定保留哪边或怎么合
（若无：写「无」）

### 将纳入本次提交的变更
- 文件列表（含**全部**新增未跟踪 / 修改 / 删除；默认全纳入）
- 排除项（仅密钥/产物/用户已点名；说明原因）
- 建议排除（待你确认）：路径 + 理由（**未获同意则仍纳入**；无则写「无」）

### 拟 commit 信息
类型（模块）：内容

### 拟执行
- [ ] 按你的冲突决定完成合并
- [ ] `git add` 相关文件（含确认纳入的未跟踪新文件）
- [ ] `git commit`
- [ ] `git push`

请确认：回复「确认」或逐条修正（commit 文案、排除文件、冲突决定）。
```

完成标准：确认包已发出（含步骤 2 的门禁结论、完整未跟踪清单、默认纳入），且尚未执行 commit/push。

## 阶段 B — 确认后提交并推送

仅当用户明确确认（或给出可执行的逐条修正）后继续。

1. 若阶段 A 曾硬停且用户未明确忽略门禁：不得进入阶段 B。
2. 按用户意见完成剩余冲突；用户说已手改的文件，重新读盘并 `git add`。
3. 再次 `git status -u`：确认无未解决冲突；**确认包标明纳入却仍 `??` 的路径必须补 `git add`**；仅用户明确排除或密钥/产物类自动排除项可保持未跟踪。
4. 按确认包中的（或用户改过的）信息一次性 commit。
5. `git push`（跟踪已有 upstream；若无 upstream，先说明将使用的 `-u` 目标并仅在用户已同意时执行）。
6. 回报：commit hash、push 结果、残留未跟踪（须说明是否用户排除）、残留 stash（若有）。

完成标准：`git status` 干净（或仅剩用户明确保留/排除的未提交文件），且 push 已成功或已说明失败原因；不得在用户未排除的情况下留下本应提交的新增文件。

## Commit 文案（全局默认）

格式：`类型（模块）：内容`

- **类型**：`feature` | `fix` | `refactor` | `docs` | `test` | `chore`
- **模块**：短英文标识（如 `frontend`、`backend`、`deploy`）
- **内容**：中文，说明为什么改 / 改动要点

示例：`feature（frontend）：增加任务列表筛选`

项目若另有强制 commit 规范（如 `feat(module): …`），以**当前仓库规则**为准，本全局默认仅在无项目规范时使用。

依据 `git diff` 起草 1 条信息，放入确认包；用户可改后再提交。

## 失败与回滚

| 场景 | 处理 |
|------|------|
| 门禁未通过 | 硬停；不 stash/pull；列出待改项 |
| pull 失败（网络/权限） | 停止；若已 stash，说明用 `git stash pop` 恢复 |
| merge 无法自动解决 | 保留冲突，写入确认包「待你处理」 |
| stash pop 冲突 | 不 drop stash（若仍存在）；列出冲突文件 |
| push 被拒绝 | 不 force；说明需再 pull 或用户决策 |
| 用户放弃 | 不 commit/push；说明如何 `stash pop` / `merge --abort`（仅在 merge 未完成且安全时） |

## 禁止

- 阶段 A 偷偷 commit/push
- 门禁未通过仍 stash/pull（除非用户本轮明确忽略门禁）
- 无确认就 push
- `push --force` / `reset --hard`（除非用户在本轮明确要求）
- 把确认包拆成多次零散提问（冲突不确定项与门禁项可列在包内，一次性问清）
- 先 pull / stash 再做门禁（门禁必须针对拉取前的本地改动）
- **擅自把未跟踪新文件移出拟提交集合**（含以「另批提交 / 主题无关 / neat 建议」为由默认排除且不经用户确认）
- 阶段 B 漏 `git add` 确认包已纳入的新增路径
